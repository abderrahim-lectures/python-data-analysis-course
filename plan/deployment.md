# GH Pages Deployment

- `.github/workflows/deploy.yml`: on push to `main`:
  1. `npm ci` + `npm run build` (Astro static output — everything the site needs, including `public/datasets/`, notebook/render pages, translated routes).
  2. Deploy the combined output via `actions/deploy-pages` (artifact path matches the Astro build output dir).
  3. **Stale step to remove**: the workflow still builds `jupyterlite-config` (via `uv … jupyter lite build`) and merges it under `build/lite`. The site no longer references `/lite/` anywhere (inline Pyodide cells replaced the JupyterLite playground in the Astro migration). The `jupyterlite-lite` build step and the `cp -r jupyterlite-config/_output build/lite` merge are vestigial — the next time CI is touched, drop both (and `jupyterlite-config/` from the repo).
- `astro.config.mjs`: `site = https://pyda-course.online/` (override with `ASTRO_SITE`), `base = '/'` (custom domain, not the repo-subpath project page). `@astrojs/sitemap` produces the sitemap.
- **Custom domain:** the site is served from `https://pyda-course.online/` rather than the default `abderrahim-lectures.github.io/python-data-analysis-course/` project-page URL, via `public/CNAME` (containing `pyda-course.online`) plus DNS pointed at GitHub Pages and the custom domain configured in the repo's Settings → Pages (both one-time, outside-the-repo steps). Because of this, `base` is `/` (root), not a `/python-data-analysis-course/` subpath — that subpath convention only applies to the default project-page URL.
- **Static-host footguns to get right up front**, since they're easy to miss until something 404s in production: for a project page *without* a custom domain, `base` must match the repo name exactly (`/python-data-analysis-course/`, not `/`) — with a custom domain and `base: '/'` as configured here, this doesn't apply, but it's worth knowing if the custom domain is ever removed. Static hosts serve `404.html` for any unmatched path — the site leans on this for `/playground/<code>` shared links (see [`playground.md`](./playground.md)). There is no `trailingSlash` config; GH Pages serves the no-slash route, and every internal link uses extensionless paths that build to directory `index.html` output.

## Staging / preview decision (2026-09-09)

- **State of reality**: the entire redesign lives on `redesign/astro-visual-novel` (~131 commits ahead of `main`), and the branch **cannot be pushed** — both `git` and `gh` tokens lack the `workflow` scope, so GitHub refuses the push (it creates/updates `.github/workflows/*.yml`, which changed for the astro@7 Node 22 bump). **No commit from the redesign has ever deployed.** `pyda-course.online` still serves the old Docusaurus site.
- **Decision**: no separate staging site is built until the branch can reach GitHub at all. The primary path stays **ship-to-`main`** (open the PR, merge, let the existing `deploy.yml` build + deploy the Pyodide-era Astro site). A dedicated `preview` branch only makes sense once the OAuth `workflow` scope is granted (re-auth the token with the `workflow` scope); at that point, `deploy.yml` can optionally gain a second trigger (`push: preview` → a separate Pages site / url) if a public staging round is wanted before launch. Not worth adding infra to a branch that can't
push.
- **Unblock needed (credential, not code)**: the developer must re-authenticate GitHub with the `workflow` scope (e.g. `gh auth refresh -s workflow` or a PAT with `workflow`). Everything else for shipping is code-complete and gate-clean (astro check 0 errors, 1086 unit tests, 44/44 smoke, contrast/responsive clean, 877 pages).
- **Deploy hygiene, carried**: `deploy.yml` still contains the vestigial `jupyterlite-config` build + `/lite/` merge steps (see above); remove them on the next CI touch (workflow file is Claude-owned; opencode did not edit it).
